# ClipNest 0.4.0 功能与性能检查

日期：2026-10-18。应用代码对应 0.4.0，检查时仓库提交为 `096f272`。
本次没有修改产品功能、替换已安装程序或发布新版；新增了可复现的性能工具和本报告。
SignPath 申请已暂停，没有提交表单。

## 环境与方法

- Windows 11 专业版，系统版本 10.0.26200；AMD Ryzen 7 9700X，16 个逻辑处理器，约 32 GB 内存。
- Release 构建，.NET 8。数据库测试调用实际 `SqliteClipboardStore`，每项预热 3 次、采样 25 次。
- 短文本每条约 512 个字符；长文本每条约 65,536 个字符。所有内容、图片和数据库均为独立生成的测试数据。
- 数据库测试包含 SQL 查询和 .NET 对象生成，不包含 WinUI 排版、绘制和输入传递。
- 使用预热后的文件缓存，未清空系统缓存。UI 启动时间为单次进程创建至出现主窗口句柄的观测，不能当作冷启动或首帧时间。
- UI 测试运行与已发布产物相同的 0.4.0 应用代码，使用独立数据目录。结束后已恢复原安装版后台运行。

| 测试集 | 主窗口句柄出现 | 进程工作集峰值 | 私有内存峰值 |
|---|---:|---:|---:|
| 110 条短文本 | 1,070 ms | 202 MiB | 171 MiB |
| 1,028 条记录，包含约 1,000 条长文本 | 901 ms | 715 MiB | 687 MiB |
| 60 张 3840 × 2160 PNG | 533 ms | 242 MiB | 212 MiB |

UI 数据集来自查询基准后的测试数据库，所以短文本有 110 条、长文本有 1,028 条，
其中 28 条为写入基准生成的短内容。这与上面的纯查询数据集并不完全相同。

长文本采样 15.3 秒，30/30 次采样时主窗口句柄可见；平均约占 5.6% 的一个 CPU 核，
折合该 16 线程 CPU 的总容量约 0.35%。图片采样 10.2 秒，20/20 次窗口可见，约占一个核的 2.9%。
这两项均保持进程响应，没有观察到崩溃。普通短文本内存观测不作为严格的持续可见 CPU 对照。

图片观测只包含初始窗口、列表缩略图与默认选中项的进程开销，**没有完成大量图片连续切换、解码峰值或持续数小时的测试**。
窗口会在失去焦点时自动隐藏，本次 UI 自动化未稳定完成逐项图片导航；不能据此声称键盘预览压力测试已通过。

## 已确认的问题

### P1：长内容场景反复加载完整正文

`MainWindow.Refresh` 在 UI 线程调用 `Search`；窗口可见且不在模态操作时每秒调用一次，搜索每次文字变化也直接调用。
`Search` 取出最多 500 条完整 `content`，之后才用 `SequenceEqual` 判断是否没有变化。
因此无变化的长文本列表也会产生约 63 MiB/秒的托管分配；真实进程中观测到了上表的内存膨胀。
长文本未命中查询 P95 约 83 ms，加上 UI 排版，存在输入卡顿风险。

建议优先让列表只取摘要及元数据，选中后再取正文；用数据变更通知或版本标记跳过重复读取，
搜索增加输入防抖和可取消的后台查询，避免旧查询覆盖新结果。

### P2：保存上限与可浏览条数不一致

设置允许保存 10–10,000 条普通历史，收藏不计入；但 `Search` 固定 `LIMIT 500`，没有分页入口，
界面仅显示“500 条”，不会提示还有更多。较旧记录仍在数据库中，知道关键词时可以搜到，
但不能靠继续滚动浏览到。测试同时验证了 500 条结果上限和最旧记录可搜索。

建议增加分批加载，并区分“已显示数量”和“总数量”。

### P2：降低历史上限不会立即处理已有记录

`SetHistoryLimit` 只修改设置，裁剪发生在 `Add` 的非重复新增分支。
测试把上限设为 10 后，长文本数据库仍保留 1,028 条（其中 100 条收藏），
928 条普通记录没有立即降为 10。仅再次复制已保存的重复内容也不会触发裁剪。

建议将调整上限后的清理作为明确操作，并同步清理被裁剪图片的文件，保留收藏。

### 条件性风险：数据库锁等待直接阻塞界面调用

外部事务被刻意保持独占锁 1.2 秒时，同步 `Search` 等待约 1,230 ms。
这是故障注入结果，不代表日常每次写入都会卡住。它说明同步 UI 查询缺少隔离，
慢磁盘或长事务出现时，锁等待会传导到界面；建议同 P1 一并处理。
